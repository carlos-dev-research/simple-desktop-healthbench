# simple-desktop-healthbench

A cross-platform desktop app (macOS, Windows, Linux), built with Flutter, for
running **[HealthBench](https://arxiv.org/abs/2505.08775)** evaluations of
language models and exploring the results.

[![CI](https://github.com/carlos-dev-research/simple-desktop-healthbench/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/carlos-dev-research/simple-desktop-healthbench/actions/workflows/ci.yml)

## About this experiment

The main purpose of this project was to **test spec-driven development (SDD)
with AI against a known objective**. The objective was to make testing and
benchmarking with the HealthBench dataset easier. The foundation was my
earlier repo,
[evals-healthbench-dashboard](https://github.com/carlos-dev-research/evals-healthbench-dashboard)
(a Python harness and local web dashboard). Its scoring formulas were kept
exactly, so the results can be compared with it.

The beginning of the session went into **crafting the specification with AI**.
That meant exploring the reference repo, the HealthBench paper and dataset,
and the Flutter desktop toolchain. The findings went into
[docs/reference/](docs/reference/). From there we wrote the project principles,
[specs/constitution.md](specs/constitution.md). Only then did code start, one
feature at a time:

```
specify → clarify → plan → tasks → implement → verify
```

Each phase ended with a human review. Every feature's spec, plan and tasks are
in [specs/](specs/) (001–006), and [CLAUDE.md](CLAUDE.md) holds the rules the AI
agent followed. Runs made with the finished app are in [results/](results/).

> **Status: version 0.2.0.** You can download and sample the HealthBench
> datasets, run evaluations, follow them live, stop and continue them, browse
> the results with median, standard deviation and bootstrap uncertainty, and
> export, import or delete run files (features 001–006). It is tested on
> macOS, Windows and Linux in CI. See [Development](#development).

## Ready-to-use app

**No build needed:** [`dist/`](dist/) contains a ready-to-use macOS app,
`HealthBench-Evals-macOS-v0.2.0.zip`. Double-click the zip, then double-click
**HealthBench Evals.app**. If macOS says it can't verify the app, see
[dist/README.md](dist/README.md).

> **The executables have only been tested on macOS** (macOS 12 or later, Apple
> Silicon and Intel). Windows and Linux are built and tested in CI, but no
> ready-to-use executables are provided for them yet. Build those from source.

## Quick start after cloning (macOS)

Follow these steps in order, the first time on a Mac. Each one is explained
in detail further down.

**Before you start:** install **Xcode** from the Mac App Store, open it once,
and let it finish installing components. Allow about 20 minutes and 3 GB of
disk space for the rest.

1. **Clone the repo and enter it**

   ```sh
   git clone https://github.com/carlos-dev-research/simple-desktop-healthbench.git
   cd simple-desktop-healthbench
   ```

2. **Run the setup script.** It installs FVM and the pinned Flutter version,
   asking before every change. Answer `y` to the prompts. The Xcode step asks
   for your Mac password, which isn't shown while you type.

   ```sh
   ./tool/setup.sh
   ```

   It should end with `✔ Final verification: all … checks passed` and
   `✔ Everything is ready.` If not, see [Troubleshooting](#troubleshooting).

3. **Optional: download the HealthBench dataset from the terminal.** You can
   skip this and download it inside the app instead (**Datasets** view, step 6).
   For the terminal, it's about 110 MB, into `healthbench/`, which git ignores:

   ```sh
   mkdir -p healthbench
   BASE=https://openaipublic.blob.core.windows.net/simple-evals/healthbench
   curl -L -o healthbench/2025-05-07-06-14-12_oss_eval.jsonl  $BASE/2025-05-07-06-14-12_oss_eval.jsonl
   curl -L -o healthbench/hard_2025-05-08-21-00-10.jsonl      $BASE/hard_2025-05-08-21-00-10.jsonl
   curl -L -o healthbench/consensus_2025-05-09-20-00-46.jsonl $BASE/consensus_2025-05-09-20-00-46.jsonl
   ```

4. **Optional: run the tests.** This confirms your copy works. It takes about a
   minute and should end with `All tests passed!`.

   ```sh
   fvm flutter test
   ```

5. **Build and open the app**

   ```sh
   fvm flutter build macos --release
   open "build/macos/Build/Products/Release/HealthBench Evals.app"
   ```

   The first build takes a few minutes. You can also drag the `.app` from that
   folder into Applications.

6. **Do a first small run.**
   1. In the app, go to **New run**.
   2. Enter your OpenAI-compatible **base URL** (for example `https://api.groq.com/openai/v1`) and your **API key**.
   3. Enter a **model under test** and a **grader model** (for example `openai/gpt-oss-20b`).
   4. Pick the dataset. If you skipped step 3: **Datasets** → **Download** next to *HealthBench (main)*, then come back and choose it under **Dataset from the library**. Otherwise use **Choose dataset file…** → `healthbench/2025-05-07-06-14-12_oss_eval.jsonl`.
   5. Set **Max conversations** to `3`, then press **Start run**.
   6. When it finishes, press **Open results**.

   See [Using the app](#using-the-app) for everything else.

**After pulling new changes** (`git pull`), rebuild:

```sh
./tool/setup.sh --check            # if the Flutter version changed, run ./tool/setup.sh instead
fvm flutter pub get
fvm flutter build macos --release
```

**Windows / Linux:** the setup script is macOS-only for now. See
[Windows and Linux](#windows-and-linux) for what to install, then use steps 3–6
with `windows` or `linux` in place of `macos`.

## What it does

HealthBench (OpenAI, 2025) is a benchmark of 5,000 realistic health
conversations. Each one has rubric criteria written by physicians. The app:

1. Sends each conversation to a **model under test** through any
   **OpenAI-compatible API**, such as OpenAI, Groq, Ollama, vLLM or LM Studio.
2. Asks a **grader model** whether the reply meets each criterion.
3. **Scores** the reply with the official formula: the points earned (penalties
   subtract) divided by the maximum positive points. The run's score is the mean
   across conversations, clipped to 0–1.
4. **Saves** each run as a self-contained file in the app's own storage (the
   sandbox on macOS). Every criterion and the whole conversation are inside,
   so results never need the dataset to be viewed.
   From inside the app, you can **delete** a run file, **export** it to any
   folder you choose, or **import** a run file you saved earlier. Import accepts
   only files that match the app's run-file format and naming pattern.
   The format is based on the
   [predecessor dashboard](https://github.com/carlos-dev-research/evals-healthbench-dashboard)'s
   format, with small changes, so it is not compatible with it.
5. **Shows** the results: a list of runs, summary tiles, the score
   distribution, and for each conversation the dialogue, the model's reply and a
   breakdown of every graded criterion.

## Using the app

1. **Datasets.**
   - **Download** the official files (*HealthBench (main)*, *HealthBench Hard*, *HealthBench Consensus*), with progress and cancel. Each download is checked against the file's known size, SHA-256 and conversation count before it's accepted.
   - **Add file…** brings in a HealthBench `.jsonl` of your own, for example an old N100 subset. It's validated first.
   - **Sample…** makes a random subset: choose the size, and the seed (40 by default). The same size and seed always give the same sample, named like `…_N100_seed40.jsonl`.
2. **New run.** Enter an OpenAI-compatible **base URL**, your **API key** and the
   **model under test** and **grader model**, each with a reasoning effort.
   The key is kept in memory only, never saved. Pick a dataset from the
   library, or choose a file. Optionally limit the run to the first N
   conversations, then press **Start run**.
3. **Progress.** The panel shows:
   - conversations done and failed;
   - the criteria graded in the current conversation;
   - elapsed and estimated time, and the score so far;
   - any skipped conversations.

   **Stop** finishes the current conversation, then stops.
4. **Runs.** Every run is listed with its status and score. Select one to see:
   - the summary tiles: the run score **± its bootstrap standard deviation**, the **median**, and the **standard deviation** of the conversation scores;
   - the score histogram;
   - every conversation, searchable and sortable. Open one to see the reply and how each rubric criterion was graded.
5. **Continue.** A stopped, failed or interrupted run shows **Continue (n left)**.
   The key from this session is filled in, and the run's dataset is picked
   from the library automatically when it's there. Only what's missing is
   graded.
6. **Export, delete, import.** On a selected run, the save icon exports an
   identical copy wherever you choose, and the bin icon deletes it (after
   confirmation). Neither is possible while the run is running. **Import**
   (top of the runs list) brings a run file back in. It's checked completely
   first, and a run with the same name is replaced only after you confirm.
   Run files are self-contained: every criterion, the conversation and the
   reference answer are inside, so results can be viewed and analysed
   without the dataset.

The form keeps everything you typed, the API key and dataset included,
while the app is open. Nothing is saved to disk, so it's empty after a
restart.

Runs and the dataset library are stored in the app's own storage. On macOS that's
`~/Library/Containers/io.github.carlos-dev-research.healthbench/`.

## Dataset

The dataset is **not** included in the repo. The easiest way to get it is the
app's **Datasets** view (see [Using the app](#using-the-app)). Files land in
the app's own storage and are verified on download.

To use the files from the terminal as well, for example with
`tool/try_run.dart`, download them into `healthbench/`, which is git-ignored:

```sh
mkdir -p healthbench
BASE=https://openaipublic.blob.core.windows.net/simple-evals/healthbench
curl -L -o healthbench/2025-05-07-06-14-12_oss_eval.jsonl  $BASE/2025-05-07-06-14-12_oss_eval.jsonl   # 5,000 conversations
curl -L -o healthbench/hard_2025-05-08-21-00-10.jsonl      $BASE/hard_2025-05-08-21-00-10.jsonl       # 1,000 (hard)
curl -L -o healthbench/consensus_2025-05-09-20-00-46.jsonl $BASE/consensus_2025-05-09-20-00-46.jsonl  # consensus
```

The files are also available on Hugging Face as
[`openai/healthbench`](https://huggingface.co/datasets/openai/healthbench) (MIT).

## Installation (macOS)

One script, [`tool/setup.sh`](tool/setup.sh), prepares a Mac to build the app.
It **explains each step, asks before every change**, and finishes by checking
that nothing else on your Mac was changed.

**Time:** about 10–20 minutes, mostly the Flutter download.
**Disk:** about 3 GB. The script warns if you have less than 10 GB free.
**You need:** an administrator account (for `sudo`) and an internet connection.

### What gets installed

| Component | Version | Why | Where |
|---|---|---|---|
| **Xcode** (the full app) | 15 or later | Flutter builds the macOS app with `xcodebuild`, which only exists in full Xcode. The Command Line Tools alone are not enough | `/Applications/Xcode.app` (you install this yourself, step 1) |
| **Homebrew** | any | Installs FVM. If it's missing, the script offers to install it | `/opt/homebrew` |
| **[FVM](https://fvm.app)** + `dartaotruntime` | 4.x | Installs the **exact Flutter version pinned in `.fvmrc`**, so every Mac builds with the same SDK. It adds only the `fvm` and `dartaotruntime` commands | Homebrew |
| **Flutter SDK** (includes Dart) | pinned in [`.fvmrc`](.fvmrc) (currently 3.47.7) | The framework and build tools | `~/fvm/versions/<version>` |

**Not installed:**
- **CocoaPods.** It isn't needed: Flutter 3.44+ uses Swift Package Manager for macOS plugins. Homebrew's CocoaPods would also put its own `ruby` and `openssl` ahead of yours on your PATH.
- **Android Studio, Chrome tooling, iOS setup.** Only the macOS desktop target is needed.

### Step 1: Install Xcode

1. Install **Xcode** from the Mac App Store (it's large, so allow time for the download).
2. Open it once and let it finish installing components, then quit it.

### Step 2: Get the code

```sh
git clone https://github.com/carlos-dev-research/simple-desktop-healthbench.git
cd simple-desktop-healthbench
```

### Step 3 (optional): Preview what's missing

```sh
./tool/setup.sh --check
```

This changes nothing. Each item is shown as ✔ (ready) or ✘ (missing).

### Step 4: Run the setup

Run it in your own terminal (VS Code's built-in terminal works). Don't use
`sudo`; the script asks for your password only where it needs it.

```sh
./tool/setup.sh
```

First it prints a **plan** of everything it might change and asks
**"Continue?"**. Then it asks about each change separately. Pressing **Enter**
means *no*, which skips that change.

| # | Step | What it asks | What happens if you say yes |
|---|---|---|---|
| 1 | macOS and disk | — | Only checks |
| 2 | Xcode | *Switch the active developer directory to Xcode? (needs sudo)* | Runs `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`. Type your **Mac login password**; nothing shows while you type. If the Xcode license or first-launch components are missing, it asks about those as well |
| 3 | Homebrew | *Run the official Homebrew installer?* (only if Homebrew is missing) | Runs the installer from https://brew.sh |
| 4 | Brewfile | Shows a **preview** first, then asks *Install fvm?* | `brew install fvm`, with nothing else upgraded, cleaned up or removed |
| 5 | Flutter | *Pin this repo to Flutter X?*, *Download Flutter X with FVM?*, *Create the .fvm/ link?* | Writes `.fvmrc`, downloads the SDK (the slow step), and links it into `.fvm/` for VS Code |
| 6 | Optional settings | *Turn off Flutter/Dart usage analytics?*, *Pre-download the macOS build artifacts?* | Both are your choice. Pre-downloading makes the first build faster |
| 7 | Project packages | *Run 'flutter pub get'?* (once the app code exists) | Downloads the Dart packages listed in `pubspec.lock` |
| 8 | `flutter doctor` | — | Prints a toolchain report (see below) |
| 9 | **Final verification** | — | **Read-only** checks (see below) |

The script is safe to run again: anything already done is skipped.

### Step 5: Check the result

**Step 9 (Final verification)** should end with
`✔ Final verification: all N checks passed`. It checks that:
- Xcode is selected, its license is accepted, and `xcrun` finds `xcodebuild`.
- `fvm flutter` runs exactly the version in `.fvmrc`, and macOS is available as a build target.
- No CocoaPods `Podfile` exists, and no secret-looking files are about to be committed.
- **No Homebrew package was upgraded, downgraded or removed**, compared with a snapshot taken before step 1.
- **`ruby`, `python3`, `openssl`, `node`, `git`, `clang` and similar commands still resolve to the same place** on your PATH.

These **`flutter doctor` warnings are expected** and can be ignored:

| Warning | Why it's fine |
|---|---|
| `[!] Android toolchain …` | We don't build for Android |
| `! CocoaPods not installed` | On purpose: Swift Package Manager is used instead |
| Errors about wireless iPhone/iPad devices | Xcode looking for nearby iOS devices; not related to this app |
| `Chrome`, `iOS` notes | Not used |

The line that matters is `• macOS (desktop) • macos • darwin-arm64` (or `darwin-x64` on Intel Macs).

### Step 6: Restart VS Code

Restart VS Code (and install the **Dart** and **Flutter** extensions if you
haven't). The repo's [`.vscode/settings.json`](.vscode/settings.json) points
the extensions at `.fvm/flutter_sdk`, so they use the pinned SDK.

### Using Flutter day to day

Always run Flutter through FVM inside this repo, so the pinned version is used:

```sh
fvm flutter --version        # should print the version in .fvmrc
fvm flutter pub get          # fetch packages (exact versions from pubspec.lock)
fvm flutter run -d macos     # launch the app (debug, with hot reload: press r)
```

If you'd like to type plain `flutter`, the script deliberately leaves that to
you. Run `fvm global <version>`, then add
`export PATH="$HOME/fvm/default/bin:$PATH"` to your `~/.zshrc` yourself.

### Troubleshooting

| Symptom | Fix |
|---|---|
| `Xcode not found` | Install Xcode (step 1). If it's not in `/Applications`, run `XCODE_PATH=/path/to/Xcode.app ./tool/setup.sh` |
| Password prompt shows nothing | Normal for `sudo`; type it and press Enter |
| `Could not determine a Flutter version` | You're offline and there's no `.fvmrc`. Reconnect, or run `FLUTTER_VERSION=3.47.7 ./tool/setup.sh` |
| `brew install` fails with "formula not found" | Your Homebrew list of available packages is stale (the script doesn't refresh it). Run `brew update` yourself, then rerun the script |
| Step 9 reports a changed package or command | Nothing else should have changed. The output shows what changed (before → after). Undo it with the table below, and please open an issue |
| VS Code can't find the Flutter SDK | Check that `.fvm/flutter_sdk` exists (rerun the script), then restart VS Code |
| Anything else | Rerun `./tool/setup.sh --check` and read the ✘ lines; each one tells you the command that fixes it |

### What the setup changes and how to undo it

The script's summary also prints these undo commands, for the changes made in that run.

| Change | Where | Undo |
|---|---|---|
| Active developer directory switched to Xcode | System-wide (`xcode-select`) | `sudo xcode-select -s <previous path>` (the script prints it; usually `/Library/Developer/CommandLineTools`) |
| `fvm` + `dartaotruntime` installed | Homebrew | `brew uninstall fvm && brew autoremove` |
| Flutter SDK and its git cache | `~/fvm` | `fvm remove <version>`, or delete `~/fvm` |
| Flutter/Dart settings and package cache | `~/.config/flutter`, `~/.dart-tool`, `~/.pub-cache` (and `~/.flutter` on some versions) | Delete those folders |
| Pinned version and SDK link | `.fvmrc` (committed), `.fvm/` (git-ignored) | `rm -rf .fvm` |
| App data (runs), once the app exists | `~/Library/Containers/<bundle-id>/` | Delete that folder. Removing the app alone does not delete it |

Never changed: `~/.zshrc` and other shell profiles, versions of tools you
already have, and anything outside the locations above.

## Development

This repo follows **spec-driven development**. Every feature moves through
`spec.md` (what and why), `plan.md` (how), `tasks.md` (steps) and finally the
implementation, and each step is reviewed before the next one starts. Specs are
in [`specs/`](specs/), and the workflow is described in [CLAUDE.md](CLAUDE.md).
The project's principles are in [specs/constitution.md](specs/constitution.md).

### Evaluation core and the developer runner

The evaluation logic lives in [`lib/core/`](lib/core/). It's pure Dart, with no
UI code, and is ported from the reference toolkit `pygrader`:

| File | Does | Ported from |
|---|---|---|
| `dataset.dart` | Reads and validates HealthBench files | `models.py` |
| `chat_client.dart` | OpenAI-compatible client with retries (408/409/429/5xx), timeouts and key redaction | the OpenAI SDK's behaviour |
| `grader_prompt.dart`, `grading.dart` | Generate the reply, grade each criterion, extract the JSON answer | `GRADER.md`, `grader.py`, `tools.get_result` |
| `scoring.dart` | HealthBench scores and the earned/missed/penalty/avoided labels | `tools.get_score` / `calculate_score` |
| `run_file.dart`, `runner.dart` | Append-only run file, progress, stop and resume | `runner.py` (plus resume) |

Until the UI is ready, [`tool/try_run.dart`](tool/try_run.dart) runs the core
from the terminal against a real endpoint. It's for developers only and isn't
part of the app:

```sh
export HEALTHBENCH_API_KEY=...        # in your shell only; never put it in a file
fvm dart run tool/try_run.dart --dataset healthbench/2025-05-07-06-14-12_oss_eval.jsonl --count-only
fvm dart run tool/try_run.dart --dataset healthbench/2025-05-07-06-14-12_oss_eval.jsonl --limit 3 \
    --base-url https://api.groq.com/openai/v1 --model openai/gpt-oss-20b --effort low
fvm dart run tool/try_run.dart --dataset healthbench/<same file> --resume build/try_runs/<run>.jsonl
fvm dart run tool/try_run.dart --validate build/try_runs/<run>.jsonl
```

Press Ctrl-C once to stop after the current conversation, and continue later
with `--resume`. Runs are written to `build/try_runs/`, which is git-ignored.

### Running the checks

These are the same checks CI runs on macOS, Windows and Linux for every push to `main`:

```sh
fvm dart format --output=none --set-exit-if-changed .   # formatting
fvm flutter analyze --fatal-infos                      # static analysis (must be 0 issues)
fvm flutter test                                       # unit, widget and project-rules tests
fvm flutter test integration_test -d macos             # launches the real app (integration_test/all_test.dart)
fvm flutter build macos --release                      # release build
```

| Test folder | What it covers |
|---|---|
| `test/core/` | The pure-Dart core (no Flutter) |
| `test/ui/` | Screens (widget tests) |
| `test/project/` | **Project rules**: the core stays free of Flutter, the version shown matches `pubspec.yaml`, macOS permissions are exactly what's allowed, no signing team, no CocoaPods, and the same app ID and name on every OS. If one of these fails, a change broke a project decision. See [the contract](specs/001-project-scaffold/contracts/project-rules.md) |
| `integration_test/` | Starts the real app on the desktop |

The release app is at `build/macos/Build/Products/Release/HealthBench Evals.app`.

## Caveats

- Model output is **unreviewed and is not medical advice**.
- Scores from random subsets, or from a grader other than OpenAI's, are **not
  comparable** to published HealthBench numbers. Grading a model with itself is
  less reliable than using an independent, stronger grader.
- API keys are used only to call the endpoint you configure. They are never
  written to run files.
